# プロバイダーのスケジュール切り替え

> CC Switch は、あなたが定義したスケジュールに従って、対応する 9 種類の CLI のアクティブなプロバイダーを自動で切り替えられます。たとえば「月〜金 09:00–18:00 は業務用の中継、それ以外は個人の API キー」といった運用です。本ガイドでは、概念・切り替えの正確な挙動・**スケジュール**ページの各操作を説明します。

## こんな方に

- 複数のプロバイダーを契約しており、それぞれを最適な時間帯だけ使いたい（夜間は安価なオフピーク中継、業務時間は公式エンドポイント）。
- チームでマシンや利用枠を共有していて、誰かが手動で切り替えるのを覚えていなくても済むようにしたい。
- Claude Code には「業務時間用」のプロバイダー、Codex には別の既定値を使いたい。スケジュールは**アプリ単位**なので、CLI ごとに独立したルールとフォールバックを持てます。

アプリごとに 1 つのプロバイダーしか使わない場合、この機能は不要です。**プロバイダー**ページのカード切り替えをそのままお使いください。

## 概念

以下の 4 つの用語が画面全体で繰り返し登場します。最初に一読しておく価値があります。

- **スケジュールルール** — `(アプリ, プロバイダー, 時間帯, 優先度, 有効, メモ)` の組み合わせで、「この時間帯はアプリ Y でプロバイダー X を使う」ことを表します。1 つのルールは 1 つのアプリにのみ属し、1 つのプロバイダーのみを指します。
- **時間帯** — `(曜日, 開始, 終了)` の 3 要素で、**マシンのローカル時刻**で評価されます。曜日は「月〜日」のチップで選択し、開始・終了は `HH:MM` 形式です。1 つのルールに複数の時間帯を持たせられます（平日午前*と*土曜午後、など）。
- **アプリ別フォールバック** — そのアプリで**有効なルールが 1 つもない**ときに切り替える先のプロバイダーです。省略可能。`— なし — （現在を維持）` にすると、時間帯外は現在のプロバイダーをそのまま維持します。
- **手動ピン（manual pin）** — 自分でプロバイダーを切り替えた場合、スケジューラは譲歩し、現在有効なスケジュール判断が入れ替わるまであなたの選択を上書きしません。ルールが有効なときはその時間帯の終了時、フォールバックだけを設定しているときは次にそのフォールバックを保存したときです。

ルールの JSON 表現（実際に保存される形です。手で書く必要はありませんが、構造の理解に役立ちます）：

```json
{
  "app": "claude",
  "provider_id": "a7f3c1e2-...",
  "windows": [{ "dow": [1, 2, 3, 4, 5], "start": "09:00", "end": "18:00" }],
  "priority": 0,
  "enabled": true,
  "note": "業務用中継・オフィス時間"
}
```

`dow` は `0` = 日曜、`6` = 土曜です。

## スケジューラの仕組み

- **チック間隔：60 秒。** スケジューラは 1 分ごとに起動し、各アプリで今この瞬間に**あるべき**プロバイダーを算出して、現在と異なれば切り替えます。さらにアプリ起動時に 1 回すぐ評価するため、時間帯の中で CC Switch を起動した場合は最大 1 分待つことなく正しいプロバイダーが有効になります。
- **アプリごとの解決順序：** 「現在」を含む時間帯を持ち、有効で、優先度が最も高いルールが勝ちます。優先度が同じ場合は、より新しく編集されたルールが勝ちます。「現在」を含むルールがなければ、そのアプリのフォールバックを使います。フォールバックも無い場合は何もしません（現在のプロバイダーを維持）。
- **現在有効な判断より手動が優先。** スケジューラは、あなたが最後に手動で切り替えた時刻と、「現在有効な判断が始まった時刻」を比較します。後者は、ルールが有効なときは現在の時間帯の開始時刻、有効なルールが無くフォールバックが設定されているときは「直前に終了した時間帯の終了時刻」と「そのフォールバックを最後に保存した時刻」のうち遅い方です。あなたの手動切り替えの方が新しければ、そのアプリはスキップされます。したがってフォールバックのみの構成でも手動切り替えは尊重されます。その場合、時間帯が存在しないためピンは境界で解除されず、次にフォールバックを変更したときに解除されます。
- **取り逃したチックは再実行されません。** マシンが 3 時間スリープしても、3 時間分の切り替えをまとめて実行することはありません。次のチックで「今」だけを評価します。
- **発火した切り替えはすべて記録されます。** トレイの表記はこれとは別の仕組みです。その記録を読み返すのではなく、現在のルールとフォールバックから再計算されており、更新されるのはトレイメニューが再構築されるときだけです（ホバーでは更新されません）。

## スケジュールページを開く

ヘッダーの**カレンダー時計アイコン**をクリックします。トレイアイコンを右クリックして**スケジュールを開く**を選ぶ方法もあり、その場合はメインウィンドウが前面に出て、スケジュールページが既に開かれていればその内容が再読み込みされます。

## ルールを追加する

1. **スケジュール**を開きます。
2. **ルールを追加**をクリックします。
3. **アプリ**を選びます。対応するすべての CLI が一覧に出ます：Claude Code、Claude Desktop、Codex、Gemini CLI、Grok Build、OpenCode、OpenClaw、Hermes、Pi。
4. **プロバイダー**を選びます。そのアプリで設定済みのプロバイダーのみが一覧に出ます。
5. **時間帯**を設定します。新規ルールには月〜金 09:00–18:00 という実用的な既定値が入っています。曜日チップを切り替え、開始・終了を編集してください。2 つ目のブロックが必要なら**時間帯を追加**をクリックします。
6. 必要に応じて**優先度**（2 つのルールが重なった場合は数値の大きい方が勝ちます）と**メモ**（自分用の目印）を設定します。
7. **有効**をオンのままにして保存します。

ルールはカードとして表示され、読みやすい時間帯の要約（`月-金 09:00-18:00`、`毎日 22:00-23:59`、それより複雑な場合は `3 件の時間帯`）が付きます。

## フォールバックを設定する

1. **スケジュール**を開きます。
2. **アプリ別フォールバック**セクションで対象のアプリを探します。
3. ドロップダウンからプロバイダーを選びます。現在時刻を含むルールが無いとき、そのプロバイダーが有効になります。
4. 時間帯外は現在のプロバイダーに触れないでほしい場合は `— なし — （現在を維持）` を選びます。

フォールバックは即時保存され、別途の確定操作はありません。

## ルールを編集・無効化・削除する

- **編集** — ルールカードの鉛筆ボタンを使います。プロバイダー・時間帯・優先度・メモ・有効フラグはすべて変更できます。既存ルールの**アプリ**は固定です。別の CLI にスケジュールを移したい場合は、そのアプリで新しいルールを作り、こちらを削除してください。
- **消さずに無効化** — ルールカードの**有効**スイッチを切ります。無効なルールは完全に不活性で、発火もしませんし、優先度の低いルールが勝つのを妨げることもありません。
- **削除** — カードの削除ボタンを使います。削除されるのはルールだけで、プロバイダー本体には影響しません。

動作確認中はワンクリックで戻せるため、削除よりも無効化が便利です。

## 手動で今すぐ実行する

ルールが機能するか確認するために 60 秒待つ必要はありません。

- **スケジュールページ → 今すぐ実行。** 結果がトーストで表示されます（例：`発火 2、スキップ 6`）。「発火」は実際に切り替えが起きたこと、「スキップ」はすでに正しいプロバイダーだった／手動ピン中だった／やることが無かったことを意味します。
- **トレイメニュー → スケジューラを今すぐ実行。** 同じ評価をウィンドウを開かずに実行します。

## 動作中に見える情報

- **トレイのツールチップ／メニュー表記** — 次の 3 つのいずれかです：
  - `スケジュール：<provider>（<time> まで）` — 今この瞬間ルールが有効。
  - `スケジュール：<provider> にフォールバック` — 現在を含むルールが無く、フォールバックが担当中。
  - `スケジュール：待機中（有効なルールなし）` — ルールもフォールバックも無い状態。
- **ページ上** — 有効なルールを持つアプリごとに**次回切り替えヒント**が 1 行表示され、次に有効になるプロバイダーと、それまでの残り時間が分かります（予定が無いアプリは表示されません）。切り替えが繰り返し失敗すると（連続 3 回以上。あるプロバイダーの設定ファイルが書き込めない場合など）、失敗回数を添えた赤いバナーが表示されます。各チックは自身の結果を記録するので、この回数は信頼できます。バナーが出たら、そのプロバイダー自身の設定を確認してください。

## ルールが紐づいたプロバイダーを削除する

スケジュールルールはプロバイダーを参照しているため、ルールの知らないところでプロバイダーが消えることはありません。**プロバイダー**ページでプロバイダーを削除すると確認ダイアログが表示され、確認するとプロバイダー本体とそれを参照していたすべてのスケジュールルールが 1 つの SQLite トランザクションでまとめて削除されます（_連鎖削除_）。どちらの段階で失敗しても、中途半端に消えた状態は残りません。確認ダイアログは何件のルールが消えるかを伝えませんが、削除の直後にトーストで削除されたスケジュールルールの件数が表示されます。

万一、存在しないプロバイダーを指したままのルールがあると、そのカードに `プロバイダーは存在しません` と表示されます。鉛筆ボタンでルールを編集して実在するプロバイダーに向け直すか、削除してください。

## このバージョンの制限

- **日跨ぎの時間帯は非対応。** 時間帯は同じ日の中で開始・終了する必要があります。`22:00–02:00` は `v1 では日跨ぎ時間帯はサポートされていません` として拒否されます。2 つの時間帯に分割してください：当日の `22:00–23:59` と、翌日のチップでの `00:00–02:00`。
- **ローカル時刻のみ。** 時間帯はマシンのローカル時計で評価されます。ルールごとのタイムゾーン指定はなく、サマータイムに合わせて時間帯をずらす挙動もありません（サマータイムが切り替わっても、壁時計上の `09:00–18:00` のままです）。
- **分単位・60 秒の解像度。** 切り替えは時間帯の境界から最大 1 分遅れることがあります。
- **1 ルールに 1 プロバイダー。** ルール内でのラウンドロビンや負荷分散はありません。時間帯の異なる複数ルールで表現してください。
- **手動ピンを解除するのは新しい判断であり、タイマーではありません。** ルールが有効なときは現在の時間帯の終了時に解除されます。次のチックを待ちたくない場合は、境界を過ぎてから**今すぐ実行**をクリックしてください。
- **フォールバックのみの構成では、フォールバックを再保存するまでピンが続きます。** フォールバックだけを設定してルールが無い場合、一度手動で切り替えると、フォールバックを再度保存するまでフォールバックは抑制されます。ピンが期限切れになる時間帯の境界が存在しないため、時間による解除もありません。これは意図的な設計です（明示的な選択が恒常的な既定値より優先されます）。ただしフォールバックが壊れたように見えるので、スケジュールページの**アプリ別フォールバック**で選び直して解除してください。

## FAQ・トラブルシューティング

**09:00 になっても切り替わりません。なぜ？**
最も多いのは手動ピンです。現在の時間帯の開始時刻以降に自分でプロバイダーを切り替えたため、スケジューラが意図的に譲歩しています。時間帯の終了を待つか、終了後に**今すぐ実行**をクリックしてください。ルールが無くフォールバックだけの場合、ピンには期限切れになる境界がありません。フォールバックを再保存すれば解除されます。次に多い原因は、ルールの**有効**スイッチがオフになっていることです。

**2 つのルールが重なっています。どちらが勝ちますか？**
**優先度**の数値が大きい方です。優先度が同じなら、より新しく編集された方が勝ちます。重なるルールには異なる優先度を付けると結果が明確になります。

**ウィンドウを閉じてもスケジュールは動きますか？**
動きます。CC Switch はトレイに常駐し、チックループもそれと共に動作します。アプリを完全に終了した場合は次に起動するまでスケジュールは動きません。起動時にはすぐ評価が走り、現在の状態に追いつきます。

**再起動してもルールは残りますか？**
残ります。ルールとフォールバックはメモリではなく CC Switch のデータベースに保存されます。

**プロバイダー以外（モデルやルーティング設定など）をスケジュールできますか？**
このバージョンではできません。ルールが切り替えるのはアプリのアクティブなプロバイダーで、これはプロバイダーカードを手でクリックするのと同じ操作です。そのプロバイダーに紐づくもの（エンドポイント、キー、モデルマッピング、ルーティング）はすべて一緒に切り替わります。

**2 つのアプリで 1 つのルールを共有できますか？**
できません。1 ルール 1 アプリです。アプリごとにルールを作成してください。「どの CLI を変更しているのか」を曖昧にしないための意図的な設計です。

**ログはどこにありますか？**
発火した切り替えはすべて記録されます。トレイの表記はその記録を読み返したものではなく、トレイメニューが再構築されるたびに現在のルールとフォールバックから再計算されています。より詳しく調べたい場合は、アプリログに `[schedule]` プレフィックス付きでチックの失敗が記録されます。
